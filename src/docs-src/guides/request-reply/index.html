Ordinary messages are opaque bytes

The relay does not interpret application payloads. send routes raw bytes; receive returns a native message with its own id, optional reply_to, sender, network, and unchanged payload. IDs and reply correlation are metadata, not a payload envelope, so arbitrary bytes (including old NWR1-looking bytes) remain opaque and count directly toward the payload limit.

A service reads application data directly from incoming.payload. Reply with reply; it targets the incoming sender/network, places the incoming ID in reply_to, and generates a distinct ID for the new message. No request kind or envelope decoding is required.

Python round trip

Connect Alice and Bob to the same matching relay as in Getting Started. This function assumes their open default membership; for another network, join both peers and pass network="team" to request. Run the service concurrently, not after awaiting the request.

{% set python_request %}import asyncio async def round_trip(alice, bob): async def serve_one(): incoming = await asyncio.wait_for(bob.receive(), timeout=5) assert incoming.payload == b"question\x00" await bob.reply(incoming, b"answer\xff") service = asyncio.create_task(serve_one()) try: response = await alice.request(bob.name, b"question\x00", timeout=5) assert response.sender == bob.name assert response.network == "default" assert response.payload == b"answer\xff" await service return response finally: service.cancel() await asyncio.gather(service, return_exceptions=True) {% endset %}{{ code_block(python_request, 'request_reply.py', 'python') }}

Call await round_trip(alice, bob) while both nodes are open. This bounded demonstration expects only one request and reply; a long-running application also needs an ordinary inbox consumer.

Node.js round trip

This example uses the locally built NWM3 Node candidate with development label 0.3.0-dev.0, not the released AR2-only 0.2.0 SDK. Follow the local candidate setup to build/install both language artifacts and run a matching NWM3 relay from the same reviewed checkout. This label does not imply registry availability. Save this ESM helper as request-reply.mjs; import roundTrip from ./request-reply.mjs, connect both clients as in Getting Started, then call await roundTrip(alice, bob) while both are open. The application owns connection cleanup.

{% set node_request %}export async function roundTrip(alice, bob) { const service = (async () => { const incoming = await bob.receive({ signal: AbortSignal.timeout(5000) }); if (incoming.payload[0] !== 1) throw new Error("expected application request"); await bob.reply(incoming, Uint8Array.of(2, 255)); })(); // Attach rejection handling immediately; settle both branches before returning. const requester = alice.request(bob.name, Uint8Array.of(1), { timeout: 5 }); const results = await Promise.allSettled([requester, service]); for (const result of results) { if (result.status === "rejected") throw result.reason; } return results[0].value; } {% endset %}{{ code_block(node_request, 'request-reply.mjs', 'javascript') }}

Operation timeout values are seconds; AbortSignal.timeout(5000) is milliseconds. For a nondefault network use { network: "team", timeout: 5 } on the requester. The service replies on incoming.network; reply has no network override.

What a matching reply proves

The waiter is registered before sending and matches reply_to to the request ID, plus expected sender name and selected network. request returns the whole native reply message, including its own ID, reply_to, and raw payload. This correlation is not authenticated identity.

  • One overall deadline covers send acceptance and reply waiting.
  • The first terminal event wins. A reader-accepted matching reply may complete before, or without, a routing receipt.
  • A prior rejection, cancellation, or deadline removes the waiter. Later replies become ordinary messages.
  • Unrelated, malformed, unsolicited, and late data remain in the bounded ordinary inbox. An ordinary receiver cannot steal a reply from an active matching waiter.

Drain the ordinary inbox concurrently

One native reader handles both ordinary data and control/reply progress. A full ordinary inbox pauses that reader, potentially delaying the reply you want and even join, leave, or close receipts. Keep an ordinary receive consumer running alongside requests; dispatch or process its messages with bounded application queues. Neither language maintains an unbounded hidden stash.

Control receipt entries and application waiters have separate max_pending/maxPending caps. Native high-water marks count messages, not total bytes; operating-system buffers also contribute. Node additionally rejects a second simultaneous native write with local_queue_full; this is not an outbound backlog.

Acceptance is not application completion

A successful send or reply means destination native queue acceptance, not remote receipt, execution, or durability. A successful request proves that a matching reply was received, not that arbitrary business work was durably committed. Design your own application acknowledgement and idempotency rules where necessary.

ReceiptTimeout, cancellation, and lifecycle interruption can occur after forwarding. They do not prove no effect. There is no automatic retry, reconnect, or replay. Do not blindly resend a timed-out mutation. Queued data can remain readable after close, and already accepted data can arrive after leave or administrator removal.

See the API reference for error and lifecycle contracts, and the CLI reference for bounded one-shot requests.
